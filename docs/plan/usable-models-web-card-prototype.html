说明栏

三个候选共用同一数据与场景；差异只在展示层。引擎应答 JSON（models[]{id,provider,model,efforts,default_effort,current,handed_off}＋note）是 331 的 owner 裁决，不动。

数据流（方案 A）

  • pkg/tool ReadableAnswer 加展示侧 Models []ReadableModel，readUsableModels 填充（旧格式回放兼容照 332）。
  • gateway readableAnswerFor 透传，空判定认新字段。
  • 前端 UsableModelsCard.vue 新组件，ToolCallCard 加 computed＋v-else-if（照 PeerRosterCard）。

不变式

  • id 零显示：id 只是发给 LLM 的派发参数，对用户无意义（TUI 裁决延伸到 web）。
  • current＝会话当前行；handed off＝已批准交接钉住的行；无档位行不画档位线。
  • 卡片是「又一条工具结果」：同 PeerRosterCard 的 padding/字号/滚动 bound，不新造盒子。

locales 键提议（zh / en）

  • chat.usableModelsCurrent：当前 / current
  • chat.usableModelsHandedOff：交接 / handed off
  • chat.usableModelsThinking：思考 / thinking
  • chat.usableModelsDefault：默认 / default
  • chat.usableModelsEmpty：没有可派发给子代理的模型。/ No model can be dispatched to a subagent.
  • chat.usableModelsEmptyHint：省略 model 参数即可使用会话当前模型。/ Omit model to run on the conversation's model.

待 owner 裁决

  • Q1 方案 A（结构化，推荐）vs B（Markdown 复用）。
  • Q2 id 在 web 同样绝不显示？（推荐：是）
  • Q3 若选 A：档位纯文本（A1）vs chip（A2）。
  • Q4 空 roster：本地化空态句＋引导（A，照 PeerRosterCard 先例）vs engine note 原句（B）。

取舍

A 是 web 原生设计语言、与 peer 卡同级、档位可做 chip；成本是引擎 DTO＋组件＋locales。B 几乎零引擎改动、两端逐字同源；成本是 Markdown 样式在卡片内未必合设计体系、分组标题只是粗体文本。推荐 A。
